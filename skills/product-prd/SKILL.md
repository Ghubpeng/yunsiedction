# product-prd（按 PRD 开发，不乱加功能）

## 1. 定位

任何新功能、新需求、行为变更，必须先形成 PRD 条目。PRD 是开发、验收、测试的**唯一依据**。

## 2. 何时使用

- 用户提出任何新功能/新需求/修改现有功能行为。
- Agent 在开发中发现“顺手做掉”的额外功能 → 必须停下来，先写 PRD。
- 例外（无需 PRD）：Bug 修复（行为回到既有定义）、纯文案/样式微调、规范内的重构。

## 3. PRD 模板（九段，缺一不可）

```markdown
## 需求标题
### 1. 背景与问题
### 2. 目标（可量化）
### 3. 用户故事 / 使用场景
### 4. 功能范围
   - In scope（做什么，逐条列）
   - Out of scope（明确不做什么，防止蔓延）
### 5. 功能详情（流程、页面、状态变化、边界情况）
### 6. 数据与规则（涉及哪些表/字段；规则是否需配置化）
### 7. 权限（哪些角色可用、数据范围）
### 8. 计费与金额（是否涉及 Token/VIP/支付；单价与规则）
### 9. 验收标准（必须可测试：给定 X → 期望 Y）
```

## 4. 强制规则（MUST）

1. 无 PRD 不写代码；PRD 未评审不进入开发。
2. 范围纪律：只做 In scope；开发中冒出的新想法 → 新 PRD 条目，禁止顺手实现。
3. 每个需求必须做**影响面分析**：涉及哪些 Skill（交给 `master-orchestrator` 生成清单）。
4. 涉及金额/权益/限额的需求，规则必须走配置化（`project-architecture` 铁律 2），PRD 中注明配置项。
5. 验收标准必须可测试，禁止写“体验良好”“性能不错”这类不可验证表述。
6. 涉及 AI 的功能必须在 PRD 中说明：调用场景、知识范围、计费方式、引用溯源要求（`ai-tutor` / `rag-knowledge-base` / `token-billing`）。

## 5. 变更流程

```
需求提出 → 写/改 PRD → 影响面分析（master-orchestrator）
        → 评审 → 更新任务 → 开发 → 按验收标准测试
```

需求变更必须回到 PRD：改需求 = 先改 PRD，再改代码。

## 6. 禁止事项（NEVER）

- “边做边设计”：没有 PRD 先搭代码再补文档。
- Scope creep：以“用户体验”为由在 PRD 之外加功能。
- 把技术方案当 PRD（PRD 描述“要什么”，不规定“怎么写”）。
- 验收标准里出现无法验证的形容词。

## 7. 与其他 Skill 的关系

- 影响面分析：`master-orchestrator`。
- 数据/权限/计费细节分别由 `database-design`、`permission-rbac`、`token-billing`、`payment-wallet` 承接。

## 8. 检查清单

- [ ] 九段齐全？In/Out scope 明确？
- [ ] 验收标准可测试？
- [ ] 影响面分析已完成并列出涉及 Skill？
- [ ] 金额/权益/限额规则标注了配置化要求？
